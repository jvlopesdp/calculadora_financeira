## Codebase Patterns
- **Worker vs SPA TypeScript split**: `src/server/` is excluded from `tsconfig.app.json` and typechecked via `tsconfig.server.json` with `types: ["@cloudflare/workers-types"]`. This keeps DOM lib out of the worker compile and avoids conflicting global types. Add new server code under `src/server/` and it gets picked up automatically.
- **Worker bindings live in `src/server/env.d.ts`** (`interface Env`). Hono routes type the env via `new Hono<{ Bindings: Env }>()`. Add every new binding/secret here _and_ wire it into `wrangler.jsonc` (`vars` for plain values, `wrangler secret put` for secrets, `d1_databases` for D1).
- **Build output structure under cloudflare/vite-plugin**: `bun run build` writes the SPA to `dist/client/` and the bundled worker + generated wrangler config to `dist/calculadora_financeira/`. The plugin rewrites paths so `wrangler deploy` uses the redirected config — never point wrangler at the source `wrangler.jsonc` directly.
- **Cloudflare custom_domain routes do NOT accept wildcards or paths.** Use `{ pattern: "calculadorafinanceira.app", custom_domain: true }`, not `calculadorafinanceira.app/*`.
- **Node 20 in the sandbox can't run wrangler directly** (needs v22). Always invoke via `bunx --bun wrangler ...` so the bun-bundled runtime is used.
- The `migrations/` directory must exist (even if empty with a `.gitkeep`) because `wrangler.jsonc` references `migrations_dir: "migrations"`.
- **Better Auth on D1**: `betterAuth({ database: env.DB })` is enough — the kysely-adapter auto-detects D1 via `batch/exec/prepare` and dynamically loads `D1SqliteDialect`. No `{ provider: 'd1' }` wrapper needed in v1.6.x. Build a fresh `createAuth(env)` per Hono request (no module-level singletons in Workers — each request has its own bindings).
- **Shared auth options pattern**: keep plugin/session/email options in `src/server/auth-options.ts` (no env deps) and re-use them in both `src/server/auth.ts` (Worker, `database: env.DB`) and `auth.config.ts` (CLI, in-memory SQLite). Prevents the CLI-generated schema from drifting from the runtime config.
- **`@better-auth/cli generate` needs a real Kysely-compatible DB** because it calls `db.introspection.getTables()`. Bun runs the CLI through jiti/Node, so `bun:sqlite` is unavailable there; the fallback is to install `better-sqlite3` (native build) or hand-write the SQL using `@better-auth/core/db/get-tables` as the source of truth. The hand-written `0001_better_auth.sql` mirrors the Kysely SQLite output exactly: lowercase DDL keywords, double-quoted identifiers, `text`/`integer`/`date` types, `references "user" ("id") on delete cascade`, indexes appended as `create index "<table>_<col>_idx"`.
- **Hono middleware registration order matters**: `app.use(path, mw)` only applies to handlers registered AFTER the `use` call. Put public routes first, then `app.use(requireUser)`, then protected routes. The `/api/*` 404 fallback can sit after the middleware safely (returns 401 for unauthed unknown routes — fine).
- **Server-side vitest pattern**: tests under `src/server/**` are picked up by `tsconfig.server.json` (workers-types only, no DOM lib). Import everything explicitly from `vitest` (no globals), mock dependencies with `vi.mock("../auth", () => ({...}))` at module top, and use Hono's `app.request(path, init, env)` to drive the middleware with a fake `Env`. Hono serializes `Date` to ISO strings when round-tripping through `c.json`, so assertions must compare `.toISOString()`.
- **Domain migrations use snake_case identifiers**, distinct from Better Auth's camelCase. Money is stored as integer cents, interest rates as basis points (1 bp = 0.01 %), and dates as ISO-8601 strings — this keeps Decimal.js reconstructions lossless. Cross-namespace FKs are fine (`financing_scenarios.user_id REFERENCES "user"("id")`), since D1 enables foreign keys by default.
- **Running migrations in sandbox**: the `db:migrate:local` script calls `wrangler` directly, which fails under Node 20. Always run via `bunx --bun wrangler d1 migrations apply <db> --local` (or `--remote`) so wrangler executes under Bun's bundled v22-compatible runtime. CI on Node 22 (US-038/039) can use the npm scripts directly.
- **Env-aware Better Auth options live in `createAuth(env)`, not `sharedAuthOptions`.** The CLI config uses `sharedAuthOptions` directly with an in-memory SQLite, and it can't see runtime bindings like `env.RESEND_API_KEY` or `env.EMAIL_FROM`. Anything that needs those — `emailVerification.sendVerificationEmail`, `emailAndPassword.sendResetPassword`, future Turnstile hooks — gets built inside `createAuth(env)` by spreading the shared block and adding the env-aware bits. Keeps the CLI generation deterministic and the runtime config single-source.
- **Mocking SDK modules in vitest**: declare a `vi.fn()` (e.g. `const sendMock = vi.fn()`) at module scope and reference it from inside the `vi.mock(...)` factory. Then `sendMock.mockReset()` in `beforeEach` and `sendMock.mockResolvedValueOnce(...)` per test. This is cleaner than reaching into the constructor's mocked implementation. Works because `vi.mock` is hoisted but the captured-by-reference variable is still patched by the time the factory runs.
- **`globalThis.fetch` spies must be (re)created INSIDE `beforeEach`**, not captured once at the top of a test. `vi.restoreAllMocks()` (in either `beforeEach` or `afterEach`) detaches the previous spy from the property; any reference held in a closure becomes a dangling spy that never observes calls. Pattern: `let fetchSpy: ReturnType<typeof vi.spyOn<typeof globalThis, "fetch">>;` at module scope, then `beforeEach(() => { vi.restoreAllMocks(); fetchSpy = vi.spyOn(globalThis, "fetch"); })`. Queue per-test responses via `fetchSpy.mockResolvedValueOnce(new Response(...))`.
- **Better Auth global hooks**: top-level `hooks: { before, after }` accept a single `AuthMiddleware` (built with `createAuthMiddleware` from `better-auth/api`). The before-hook fires for every endpoint after the router parses the body but BEFORE the endpoint's zod schema runs — so `ctx.body` carries the raw parsed body (unknown fields intact). This matters for /sign-in/email, whose `signInEmailBodySchema = z.object({...})` strips unknowns; only /sign-up/email uses `.and(z.record(z.string(), z.any()))` and would keep them at endpoint time. Match endpoints via `ctx.path === "/sign-up/email"` etc. (paths are relative to `/api/auth/`, not absolute). Throw `new APIError("BAD_REQUEST", { message, code })` from `better-auth/api` to fail the request as a 400 JSON.
- **Better Auth client on the frontend** is the same `better-auth` package, imported from `better-auth/react` (the `./react` subpath export). `createAuthClient({ baseURL })` returns an object whose `useSession()` is a React hook returning `{ data, isPending, isRefetching, error, refetch }`. Derive `AuthUser` / `AuthSession` via `ReturnType<typeof authClient.useSession>['data']` instead of reaching for internals — the React client doesn't expose `$Infer`, only the vanilla one does.
- **Mocking the authClient in jsdom tests**: instantiating the real `createAuthClient` in jsdom pulls in nanostores' session refresh, focus/online managers, and `BroadcastChannel` — heavy and flaky. Pattern that avoids it: declare `const useSessionMock = vi.fn()` at module scope and `vi.mock("./auth-client", () => ({ authClient: { useSession: () => useSessionMock() } }))`. Each test calls `useSessionMock.mockReturnValue({ data, isPending, ... })`. `renderHook` from `@testing-library/react` then exercises `useCurrentUser()` cleanly.
- **Router factoring**: `App.tsx` does ONLY `<BrowserRouter><AppRoutes/></BrowserRouter>`; the route table lives in `src/app/routes.tsx` exporting `<AppRoutes/>`. Tests use `<MemoryRouter initialEntries={[path]}><AppRoutes/></MemoryRouter>` — wrapping `<App/>` instead would nest two routers. Layouts (`AppShell`, `AuthLayout`) and gates (`ProtectedRoute`) are layout routes that render `<Outlet/>`: `<Route element={<AppShell/>}><Route path="/foo" .../></Route>`. ProtectedRoute also a layout route — wrap a Route group with `<Route element={<ProtectedRoute/>}>...</Route>` so the gate runs once and all children inherit. Page components live under `src/features/<area>/pages/<route>-page.tsx`; the `app/` dir holds router-only chrome (shells, gates, 404).
- **shadcn `Form` component** lives at `src/components/ui/form.tsx` (hand-written because `bunx shadcn add form` failed offline). Uses our existing `Label` (not `@radix-ui/react-label`) and `@radix-ui/react-slot` for `FormControl`. Standard usage: `<Form {...form}><form onSubmit={form.handleSubmit(...)}><FormField control={form.control} name="x" render={({field}) => <FormItem><FormLabel>…</FormLabel><FormControl><Input {...field}/></FormControl><FormMessage/></FormItem>}/></form></Form>`. `FormMessage` auto-renders the zod error for the field — don't render error text manually.
- **Sending extra fields to typed Better Auth endpoints**: `authClient.signUp.email` / `signIn.email` have STRICT TS types (`InferSignUpEmailCtx` in `better-auth/dist/client/path-to-object.d.mts`) that don't accept unknown keys. To smuggle extras (e.g. `turnstileToken`) past the type check, put them in `fetchOptions: { body: { … } }` — the client proxy merges that into the POST body before sending, and the Worker's before-hook still reads them off `ctx.body`. Confirmed working in `src/features/auth/pages/register-page.tsx`.
- **Turnstile dev bypass on the frontend**: `<TurnstileField onToken={…}/>` (in `src/features/auth/components/`) skips the real widget when `VITE_TURNSTILE_SITE_KEY` is empty and fires `onToken("dev-token-no-site-key")` immediately. The Worker's `verifyTurnstile` bypasses on the same condition (empty `TURNSTILE_SECRET_KEY` → returns `true`). Keep these in sync: changing one without the other breaks dev mode.
- **Testing auth pages in jsdom**: mock `@/lib/auth-client` with a module-scope `vi.fn()` to stub the endpoint(s) you care about; mock `@/features/auth/components/turnstile-field` with a button stub that calls `onToken` synchronously. Together these keep tests fast and deterministic — no real Turnstile script load, no real `createAuthClient` nanostores boot, no network. Wrap with `<MemoryRouter initialEntries={[path]}>` + `<Routes>` containing the source page + simple `<div>` placeholders for destinations so post-submit navigation can be asserted via `screen.findByText(...)`.

Pattern: `vi.mock("@/components/ui/dropdown-menu", () => ({ DropdownMenu: Passthrough, DropdownMenuTrigger: Passthrough, DropdownMenuContent: Passthrough, DropdownMenuItem: ({ onSelect, children }) => <button role="menuitem" onClick={() => onSelect?.()}>{children}</button>, ... }))`. When adding new routes under `<AppShell>`, extend `getPageTitle` so the header label is consistent — and search `**/*.test.tsx` for the old/new title strings to update coupled assertions in page-level tests (`App.test.tsx`, `<page>-page.test.tsx`).
- **Inverse engines for finance reuse the MVP prepayment helpers**: any function that resolves a desired-payment-shape input (`resolveExtraFromTargetPayment`, future "target term" / "target end date" helpers) computes the implied extra in Decimal and delegates to `applyPrepaymentReduceTerm` or `applyPrepaymentReduceInstallment` — never re-implementing the month-by-month walk. The reduce-installment engine has an explicit zero-extra short-circuit that returns the base PRICE/SAC schedule row-for-row, so the `extra = 0` boundary case is exact without special-casing in the caller. Use pt-BR error messages via `formatBRL` for the displayed bound (e.g. "Parcela desejada deve ser ≥ R$ X").
- **`CurrencyInput` tests must use `formatBRL(value)` for monetary inputs, not `value.toString()`**: `parseBRL` strips ALL dots as BRL thousand separators (`.replace(/\./g, "")`), so typing `"4615.30"` into a CurrencyInput is parsed as **461530**, not 4615.30. Pattern: `fireEvent.change(input, { target: { value: formatBRL(target) } })`. Plain integers (`"500"`, `"0"`) work because they contain no decimal point. This blew up the entire `target-payment-card.test.tsx` in US-017 with absurd "extra=657330.55" results before the fix.
- **Schema-with-dynamic-bound vs static-schema + inline check**: react-hook-form's `useForm({ resolver: zodResolver(schema) })` captures the resolver once. Rebuilding `schema = useMemo(() => createSchema(boundFromState), [bound])` creates a stale resolver — the form won't re-evaluate against the new bound when state changes. Pattern when the bound comes from a *different* form (e.g. `basePriceInstallment` derived from the financing form): keep zod static (type/finite/positive checks), then add a `useMemo<string | null>` inline error against the live state, and render `inlineError = schemaError ?? boundError` into the same `text-destructive` slot.
- **Cross-card simulation state via `useSimulation`**: the financing form publishes to `financing`; downstream cards read it and may publish their own derived state. The target-payment card reads `financing`, computes the base PRICE installment + extra, and publishes the derived `extraMonthly` so charts/amortization-table/excel/results — which still consume `extraMonthly` + `extraStrategy` — keep working unchanged. When swapping an input UI, keep writing the same canonical state to the context to avoid touching every downstream consumer in the same story.
- **Shared `resolveExtraSchedule(inputs, extra, strategy)` helper** in `src/core/finance/extra-schedule.ts` is the single chokepoint for "schedule under monthly extra payment". For PRICE it routes through `resolveExtraFromTargetPayment` (so charts/Excel see the same engine the UI uses for "parcela desejada"); for SAC it falls back to `applyPrepaymentReduceTerm`/`applyPrepaymentReduceInstallment`. New downstream consumers should call this instead of the prepayment engine directly.
- **Rent-vs-buy engine delegation**: `simulateRentVsBuy` (new "Investidor Sardinha"-style) is the canonical month-by-month wealth simulator. The legacy `compareRentVsBuy` (MVP shape with `monthlyRate`, `annualAppreciation`, no purchase/sale costs) is kept as a thin wrapper that delegates with `purchaseCostPct=0`, `saleCostPct=0` and maps the new `{paidInstallment, monthlyOwnershipOutflow, investedDifference, rentPaid}` outputs back to the old `{investedCapital, rent}` shape. New rent-vs-buy callers (US-020+) should target `simulateRentVsBuy` directly so they pick up purchase/sale frictions by default. Decimal-typed input fields are nullable defaults — pass `?? ZERO` if not user-provided.

- **Learnings for future iterations:**
  - The MVP-compat wrapper needs its own input-shape validation BEFORE the conversion to the new engine's inputs, so legacy error messages keep their old field names (e.g. `monthlyRate` vs `annualRate`). Otherwise the error message says `annualRate` and breaks tests like `compareRentVsBuy — validation > throws when monthlyRate is negative`. Cheapest fix: a single early check (`if (inputs.monthlyRate.isNegative()) throw new Error("monthlyRate must be non-negative")`) before delegating; the rest of the validation can be delegated since the new error messages are field-name-stable for the shared fields.
  - When you delegate an MVP function to a new engine and the new engine has different semantics at m=0 (e.g. new `rentPaid=0` at m=0 vs old `rent=monthlyRent`), don't try to align the new engine. Just patch the mapping in the wrapper: `rent: idx === 0 ? roundMoney(inputs.monthlyRent) : r.rentPaid`. Future code reading the new shape gets the correct "what was paid this month" semantics; legacy code keeps the "what rent applies this month" semantics.
  - Purchase costs default to a non-zero value (0.03) in the new engine, which means the renter starts ahead by `propertyValue · purchaseCostPct` in net worth. Any break-even / scenario test that assumes both sides start at parity must EITHER zero out both purchase/sale costs OR adjust expectations accordingly. The first tests I wrote for break-even with `purchaseCostPct=0` and `saleCostPct=0` immediately reported `breakEven=1` because both sides started exactly equal.
  - `Decimal.pow(ONE.div(12))` is the canonical way to take the 12th root in decimal.js (it accepts a `Decimal` exponent, no need for `Math.pow`). Reused for both `annualToMonthlyRate` and the renter's per-month investment compounding.
  - `saleCostPct >= 1` must be validated (rejecting `1.0`) — otherwise the buyer's "net sale proceeds" would be zero or negative, producing nonsense net-worth values. Match the validation message format (`{field} must be ...`) used elsewhere in the file so the test regex matches the field name.
