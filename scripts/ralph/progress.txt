## Codebase Patterns
- Theme tokens live in `src/index.css` (`:root` light + `.dark`) and are exposed as Tailwind utilities via `@theme` (`--color-*`). Use semantic classes (`bg-background`, `bg-primary`, `text-primary-foreground`, `text-foreground`, `text-muted-foreground`) instead of hex colors so light/dark mode stay consistent. `--primary` ≈ the brand red (#B94F45), `--background` ≈ the brand creme (#F7EFE2).
- Quality gate: `bun run typecheck`, `bunx eslint <file>` (or `bun run lint`), `bun run test`. tsc emits a harmless `setlocale` warning — exit code is what matters.
- `bun` may not be available in every sandbox — fall back to `node_modules/.bin/tsc -b --noEmit`, `node_modules/.bin/eslint <files>`, and `node_modules/.bin/vitest run`. Exit code 0 == pass.
- **Vitest in this sandbox**: the harness sometimes back-runs vitest as a background task and the `.done` sentinel never fires, hanging Ralph. Workaround: launch `vitest run` and then `until grep -q "Test Files" /tmp/.../<id>.output; do sleep 5; done` to wait for the trailing summary line. Don't chain `| tail` directly to vitest — that's what triggers the background detector.
- No browser/MCP tooling available in this environment; UI stories' "Verify in browser" AC must be flagged as needing manual verification.
- `BrandLogo` (`src/components/brand/brand-logo.tsx`) wraps the wordmark in a `bg-primary` contrast strip — the wordmark SVG is white text, so any caller showing it on a light surface relies on this strip. If you ever need the wordmark *without* the strip (e.g. when it's already on a dark surface), the strip is hideable via `containerClassName="hidden ..."` instead of editing the component (see `app-sidebar.tsx` for the mobile case).
- **Select (Radix/shadcn)**: `src/components/ui/select.tsx` exports the canonical shadcn surface (`Select`, `SelectTrigger`, `SelectValue`, `SelectContent`, `SelectItem`, plus `SelectGroup`/`SelectLabel`/`SelectSeparator`). Controlled via `value` + `onValueChange` (not `onChange`). With `react-hook-form`, wrap with `<Controller>` (or use a `<FormField>`) and pass `field.value`/`field.onChange` — `register("name")` does NOT work because the trigger is a `<button>`, not a `<select>`. The trigger button is what receives `id` for `Label htmlFor`. A test-only mock at `src/tests/select-mock.tsx` (exported as `selectMock`) renders a real native `<select>` so `fireEvent.change(select, { target: { value } })` keeps working — register it via `vi.mock("@/components/ui/select", async () => (await import("@/tests/select-mock")).selectMock)`.
- **D1 migrations**: live in `migrations/NNNN_*.sql`, applied via `bun run db:migrate:local` (local) / `db:migrate:remote` (prod, run automatically before deploy). Plain SQL; no inline JS. Two important quirks: (a) D1 doesn't ship a portable `POW`/`POWER` — compute compounded values in app code (Decimal.js) before INSERT, not in SQL; (b) for data-migrations across tables, use `INSERT OR IGNORE INTO target (...) SELECT ... FROM source` and watch out for UNIQUE constraints on the target. Sandbox NOTE: Wrangler v4 requires Node 22+, so `db:migrate:local` cannot run here on the default Node 20 — review SQL by hand and document the limitation in the story's progress entry.

Compose in the page with `useMemo`, render via `<SectionCards items={…}/>`. - **Optimistic mutation re-render flow** (as of US-013): pages that derive UI from a React Query cache key should keep all derived state behind `useMemo([data])` — never duplicate the computed values into local state. The optimistic update inside `useUpsertTrackerEntry`/`useDeleteTrackerEntry` writes to the same `trackerPlanQueryKey(planId)` that `useTrackerPlan` reads, so any consumer (`AcompanhamentoDetailPage` for KPIs/chart, `TrackerSpreadsheet` for the table) re-renders automatically with the new data. To unit-test the real-time recompute end-to-end (not just the spreadsheet), wrap the page in a real `QueryClient`, stub only `fetch` (route `/api/tracker/plans/:id` for GET and `/api/tracker/plans/:id/entries` for POST), and drive the save through the existing `Valor pago no mês N` input + `Salvar` button. Mock chart + dialog (Radix portals); use the canonical `selectMock` for the row Select.
- **ScheduleMonth.scheduledInstallment vs installment** (as of US-012): all tracker schedules (`normalSchedule`/`realizedSchedule`/`goalSchedule`) emit two installment fields per row. `installment` = valor efetivamente desembolsado no mês (= o lançamento, ou o pagamento de quitação na linha final, ou a parcela vigente em meses sem lançamento). `scheduledInstallment` = parcela vigente no INÍCIO do mês, *antes* do lançamento. Em `normalSchedule` (e em qualquer schedule sem extras) os dois são iguais. Em `realizedSchedule`, após um lançamento `reduce_installment` com excedente positivo, todos os meses seguintes têm `scheduledInstallment` recalculado (menor). **Use `realizedRow.scheduledInstallment` (não `normalRow.installment`) para qualquer coluna "Parcela prevista" — caso contrário a UI mostra o cronograma original mesmo após reduções**. O engine guarda recálculo apenas quando `paid - scheduled > R$ 0,01` para evitar drift de arredondamento ao pagar exatamente a parcela vigente.

Qualquer story futura que adicione uma nova mutation precisa replicar o passo (b) — caso contrário a UI fica "fria" até um refetch manual.
  - Para testar real-time de uma página inteira, escolha entre dois padrões: (i) mock do `useTrackerPlan` + `rerender()` com novos dados (rápido, foca no useMemo wiring); (ii) `QueryClient` real + apenas `fetch` mockado (mais lento, mas exercita as mutations otimistas reais).
