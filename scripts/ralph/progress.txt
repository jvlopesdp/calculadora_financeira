## Codebase Patterns
- Project root is `/workspace` (Vite project lives at the repo root, not in a subdir).
- Use Bun as the task runner: `bun install`, `bun run typecheck`, `bun run lint`, `bun run test`, `bun run build`. Scripts are defined in `package.json`.
- Tailwind v4 + `@tailwindcss/vite` plugin (no `tailwind.config.js` — theme tokens come from `src/index.css`, copied from `/index.css` tweakcn export).
- Path alias `@/` -> `./src/` is set in both `vite.config.ts` and `tsconfig.app.json` — use `@/lib/...`, `@/core/finance/...`, etc.
- `vite.config.ts` imports `defineConfig` from `vitest/config` (single config file for both Vite and Vitest — avoids dual-vite type-conflict).
- shadcn/ui is initialized via `components.json` (style: new-york, baseColor: neutral, cssVariables: true). Add components with `bunx shadcn@latest add <name>`. DiceUI uses the same registry mechanism: `bunx shadcn@latest add "https://diceui.com/r/<component>.json"`.
- ESLint config (`eslint.config.js`, flat config) enforces `@typescript-eslint/no-explicit-any: error` and ignores `src/components/ui/**` (shadcn-generated code).
- ESLint also enforces `no-irregular-whitespace`. If you need to match U+00A0 / U+202F (NBSP / narrow NBSP from `Intl.NumberFormat`), build the regex via `new RegExp("[\\u00A0\\u202F]", "g")` instead of writing the literal NBSP inside a `/.../` regex literal.
- Tests live next to source as `*.test.ts(x)` or in `src/tests/`. Global `expect`/`describe` available (vitest globals + `@testing-library/jest-dom/vitest` matchers).
- Vitest uses jsdom environment; setup file at `src/tests/setup.ts`.
- CI runs on push/PR to `main`: install -> typecheck -> lint -> test -> build (`.github/workflows/ci.yml`).
- pt-BR formatters live in `src/lib/formatters/`: `currency.ts` (`formatBRL`), `percentage.ts` (`formatPercentage` / `parsePercentage`), `number.ts` (`formatInteger` / `formatMonths`). Reuse these everywhere — never re-roll a `toLocaleString` call inline.
- `Intl.NumberFormat("pt-BR", { style: "currency", currency: "BRL" })` returns the symbol joined to the number with U+00A0 (and sometimes U+202F on newer ICU). The formatters strip those to a plain ASCII space so tests, snapshots, and Excel export are deterministic — keep that normalization step if you fork them.
- `formatPercentage` expects the value in **percent units** (e.g. `1.25` → `"1,25%"`), not a fraction. Internally it divides by 100 before passing to the percent-style Intl formatter. `parsePercentage` is the inverse and tolerates an optional `%`, whitespace, and pt-BR thousand/decimal separators.
- Decimal.js global precision/rounding is configured **once** in `src/core/finance/financial-types.ts` (`Decimal.set({ precision: 30, rounding: ROUND_HALF_EVEN })`). Any new finance module must import from `./financial-types` (or transitively, e.g. via `price-calculator`) so the side-effect runs before arithmetic.
- Money rounding helper: `roundMoney(value: Decimal)` in `financial-types.ts` rounds to 2dp using `ROUND_HALF_EVEN`. Use it for every monetary cell that gets recorded into a `ScheduleRow` — never call `.toDecimalPlaces` directly inside engine code so the rounding mode stays consistent.
- `Decimal#toString()` strips trailing zeros (e.g. `new Decimal("10100.00").toString() === "10100"`). For 2dp display assertions use `toFixed(2)` or compare with `.equals()`. Prefer `.equals(n)` in tests over string equality.
- Schedule rounding convention: round the base PRICE installment **once** at start, round each row's interest to 2dp from the running balance, derive amortization as `installment - interest`, and let the **final** row's amortization equal the remaining balance (final installment = balance + final-interest, may differ from base installment). This guarantees `last.balance === 0` exactly and `sum(amortization) === principal` exactly.
- Vitest matcher names follow Jest conventions: `toBeLessThanOrEqual` / `toBeGreaterThanOrEqual` (no trailing "To"). Decimal.js uses `.lessThanOrEqualTo` / `.greaterThanOrEqualTo` — different method, different name. If you mistype the matcher, Vitest throws "Invalid Chai property" with a suggestion.
- Prepayment schedules use `PrepaymentScheduleRow extends ScheduleRow` with two extra fields: `baseInstallment` (the row's "would-be" base for the strategy) and `extraPayment` (extra applied that month). Invariant: `baseInstallment + extraPayment === installment` and `interest + amortization === installment`. On partial final rows, cap recorded extra at the user-supplied cap via the `splitFinalPayment` helper so the zero-extra case doesn't leak rounding residuals into `extraPayment`.
- Annual-to-monthly rate conversion lives in `rent-vs-buy.ts` as `annualToMonthlyRate(annual)` = `(1 + annual)^(1/12) − 1` (Decimal.js `pow` with a fractional exponent). Reuse this helper for any future feature that needs to convert an annual return/appreciation/inflation rate to a per-month compounding rate so the precision setup stays consistent.
- Symmetric rent-vs-buy model: each month the lower-spending side invests `|buyOutflow − rentOutflow|` (no borrowing — the higher-spender contributes nothing). Both parties' invested capital grows by the monthly investment rate **before** the new contribution is added. Property value compounds monthly from the annual appreciation rate. Rent steps up at month 12, 24, 36, ... by `(1 + annualRentAdjustment)`. Net worth at month m = `propertyValue − outstandingBalance + investedCapital` (buy) and `investedCapital` (rent). Negative net worth is allowed.
- Rent-vs-buy timelines include month 0 as the starting state, so timeline length is `horizonMonths + 1` (m=0..horizon). At m=0 both sides start tied at `downPayment` net worth (buyer paid it as down payment, renter invested it). Break-even is the first m ≥ 1 where `buy.netWorth >= rent.netWorth`; if buy never catches up, `breakEvenMonth` is `null`. Tie tolerance for `bestScenario` is R$ 0.01 (matches money rounding).
- Zod form schemas live in `src/features/simulator/schemas/`: `financing.ts`, `prepayment.ts`, `rent-vs-buy.ts`. They validate the **form layer** (plain numbers), not the engine layer (Decimal). The form/hook layer converts numbers to Decimal before calling the engine. Reuse these via `zodResolver` in React Hook Form. All error messages are pt-BR.
- Zod 3.25 still supports the v3 classic API: `z.number({ required_error: "...", invalid_type_error: "..." })`. Use this pattern for every form field so missing values, wrong types, and out-of-range numbers each get a distinct pt-BR message. The default `z.number()` message ("Required" / "Expected number, received string") is in English — always override.
- Cross-field rules (e.g. `downPayment < propertyValue`) go in `.refine(...)` with `path: ["fieldName"]` so the error surfaces below the right input. Test by asserting `result.error.issues.find((i) => i.path.join(".") === "fieldName")?.message`.
- Tests using `safeParse` should grab errors via a small helper `firstErrorFor(result, path)` instead of relying on `error.flatten().fieldErrors[path][0]` — the latter loses cross-field refines that target a single field.
- When testing "missing value" via destructure-and-omit, ESLint's no-unused-vars rule complains about the destructured placeholder. Name the placeholder `_omit` and add `void _omit;` so the destructure has a referenced variable. Don't try `_` (collides with other ignored vars) and don't disable the rule per-file.
- React context + hook + provider: split into two files. The `createContext` call and the consumer hook (e.g. `useTheme`) live in a `.ts` file (no JSX, exports only constants/types/hook); the `<Provider>` component lives in a `.tsx` file that imports from the context file. This satisfies eslint-plugin-react-refresh's `only-export-components` rule, which would otherwise warn when a `.tsx` file exports both a component and a hook/constant. Same pattern shadcn uses for its theme provider.
- shadcn CLI (`bunx shadcn@latest add <name>`) requires network access to https://ui.shadcn.com; the sandbox has none. When you need a shadcn component, hand-roll it in `src/components/ui/<name>.tsx` using the new-york-style source (the file is ESLint-ignored already, so the typical shadcn idioms — `React.forwardRef`, `cva` variants, `cn(...)` from `@/lib/utils`, `Slot` from `@radix-ui/react-slot`, `displayName` — pass without changes).
- Theme-class convention: this project's tweakcn `index.css` uses `.dark` as the toggling class (via `@custom-variant dark (&:is(.dark *))`), applied to `document.documentElement` (`<html>`). The provider must add/remove the literal class name `dark` on `<html>` (not `<body>`, not a custom name) for the existing CSS-variable overrides in `.dark { ... }` to take effect.
- jsdom + matchMedia: jsdom doesn't ship a `window.matchMedia` implementation. In tests, stub it via `Object.defineProperty(window, "matchMedia", { configurable: true, writable: true, value: ... })` returning a fake `MediaQueryList` with `addEventListener`/`removeEventListener` that track listeners — then trigger `change` events manually to test the OS-preference subscription. `vi.stubGlobal` alone isn't enough because the `window` property is non-writable by default.
- App shell lives at `src/app/App.tsx` (not `src/App.tsx`). The entry import in `src/main.tsx` is `import App from "@/app/App"`. Keep this layout — future page-level wiring (`useSimulation`, context providers, etc.) goes under `src/app/`.
- shadcn primitives we hand-roll go in `src/components/ui/`. So far: `button.tsx`, `card.tsx`. ESLint already ignores that folder so the typical `React.forwardRef` + `cn(...)` + `displayName` idioms pass without changes. Reuse `Card`/`CardHeader`/`CardTitle`/`CardDescription`/`CardContent` across the simulator cards — don't redefine the visual shell per feature.
- App-level layout convention: outer `<main class="mx-auto max-w-screen-xl ...">` + inner `<div class="flex flex-col gap-6 md:grid md:grid-cols-12 md:gap-6">`. Each section card sets its own `md:col-span-*`. Below the `md` (768px) breakpoint the cards stack vertically (`flex-col`); above it they fall into a 12-column grid. Header is `<header class="sticky top-0 z-40 ... shadow-sm">` so it pins on scroll.
- Reusable finance inputs live in `src/components/finance/`: `currency-input.tsx` (BRL) and `percentage-input.tsx`. API: `value: number | null` + `onChange: (v: number | null) => void` + optional `decimals` (percent). Internal display state; raw editable on focus, formatted on blur. `onChange` fires on every keystroke (parsed) so RHF validation can be `mode: "onChange"`. Reuse these via RHF `Controller` — never re-roll inline `<input>` masking.
- pt-BR currency parser: `parseBRL(input: string): number | null` lives in `src/lib/formatters/currency.ts` alongside `formatBRL` (mirrors `parsePercentage`/`formatPercentage`). Tolerates `R$`, NBSP/whitespace, pt-BR thousand dots, and decimal commas; returns `null` for blanks/non-numeric input.
- Page-level state context: `src/features/simulator/hooks/simulation-context.ts` (context + `useSimulation()` hook, .ts no JSX) + `simulation-provider.tsx` (component). Same two-file split shadcn/our theme provider uses to satisfy `react-refresh/only-export-components`. `SimulationProvider` wraps `<App />` in `src/main.tsx` and in test renders.
- Hand-rolled shadcn primitives we have so far: `button.tsx`, `card.tsx`, `input.tsx`, `label.tsx`, `select.tsx`. The Select primitive is a styled native `<select>` (no `@radix-ui/react-select` dep) — keeps the bundle slim and works fine with RHF `register`. Reuse these everywhere; do not redefine per-feature.
- RHF + zodResolver + nullable defaults: `useForm<FormShape>({ resolver: zodResolver(schema), mode: "onChange", defaultValues })` where `FormShape` has nullable fields (`number | null`). Do NOT pass the 3-generic form (`useForm<TFieldValues, TContext, TTransformedValues>`) — it conflicts with zodResolver's inferred output type when nullable fields refine to non-null. Inside `handleSubmit`, cast values to the schema's output type if downstream needs the strict shape.
- Zod `.refine()` cross-field rules (e.g. `downPayment < propertyValue`) only fire when **every** individual field validation passes. In a UI test that wants to surface the refine message, fill in **all** required fields with valid values first, then introduce the cross-field invariant violation in the field of interest. Otherwise the refine never runs and the message never appears.
- Derived read-only fields use `<output>` (not `<input readOnly>`) so screen readers announce updates via `aria-live="polite"` and the `getByLabelText` query still resolves (label `htmlFor` works on `<output>` too). Style with the same `border-input bg-muted ...` classes as inputs for visual consistency, plus `.font-tabular` for monetary values.

- **Learnings for future iterations:**
  - Configure Decimal.js once per process. I put the `Decimal.set` call at module scope in `financial-types.ts`; every other finance module imports from there, which guarantees the precision/rounding is applied before any `Decimal` math runs in the engine. Don't sprinkle `Decimal.set` calls in feature code.
  - PRICE base installment formula: `P · i · (1+i)^n / ((1+i)^n − 1)`. With `i = 0`, the formula is undefined (0/0); explicitly branch to `P/n`. Keep this branch — Zod allows rate > 0 in the form (US-007), but the engine must still tolerate `0` so callers can compose it with future rate-curve features.

  - `Decimal#toString()` does **not** preserve trailing zeros: `new Decimal("10100.00").toString() === "10100"`. Don't compare to `"10100.00"` in tests — use `.equals()` or `.toFixed(2)`.
  - When you need a quick golden fixture, write the implementation first then `bun -e "import('./src/core/finance/...').then(...)"` to compute the actual rounded value, and lock that into the test. Faster and more accurate than mental log/exp math.
  - Empty-schedule guard (`termMonths <= 0` → `[]`) makes the function safer for UI code that might bind to a half-filled form before validation runs.

## 2026-05-15 - US-004 — SAC financial engine (installment + schedule)
- Added `generateSacSchedule(inputs)` to `src/core/finance/amortization.ts`. Mirrors the PRICE row shape (`ScheduleRow`) and reuses the same `roundMoney` helper + `final-row absorbs residual` pattern, so PRICE and SAC have identical output contracts and zero-balance guarantees.
- Algorithm: base amortization = `roundMoney(principal / termMonths)`, constant for rows `1..n-1`. For each month: `interest = roundMoney(balance * monthlyRate)`, `installment = roundMoney(amortization + interest)`, `balance = balance - amortization`. The final row sets `amortization = balance` so the closing balance lands exactly at 0 and `sum(amortization) === principal`.
- Tests added to `src/core/finance/amortization.test.ts` cover the 360-month golden fixture (first installment R$ 3.233,33, juros R$ 2.400, amort R$ 833,33, balance R$ 299.166,67; second-row regression for monotonic decrease; constant amortization invariant for rows 1..n-1; installment non-increasing; interest strictly decreasing; final balance = 0; `interest + amortization === installment`; total amort = principal), 1-month edge case, zero-rate edge case, balance-zero invariant on 4 (principal, rate, term) combos, and the `sum(SAC interest) < sum(PRICE interest)` invariant on 4 combos.
- Files changed: `src/core/finance/amortization.ts`, `src/core/finance/amortization.test.ts`, `scripts/ralph/prd.json`, `scripts/ralph/progress.txt`.
- Quality checks: `bun run typecheck` ✅, `bun run lint` ✅, `bun run test` ✅ (83 tests across 6 files, 21 new SAC cases), `bun run build` ✅.
- **Learnings for future iterations:**
  - SAC installments are NOT strictly monotonic in pathological corners — with rounded constant amortization, the final residual row's amortization may be slightly larger than the base, and zero-rate cases collapse to all-equal installments. Write the test as `lessThanOrEqualTo` ("non-increasing"), not `lessThan`. The PRD AC text "decreases monotonically" describes the algorithmic intent, not a strict test assertion.
  - SAC residual is bounded: with HALF_EVEN rounding to 2dp, the per-month rounding error is ≤ 0.005, so over `n` months the residual is ≤ `n * 0.005`. For typical `(P, r, n)` the interest drop dominates the residual growth, so the final installment still ends up lower than the previous one — but don't rely on it for tests, use the non-strict comparator.
  - Generating the golden fixture: run `bun -e "..."` against the engine to lock in the actual rounded numbers (`first installment 3233.33`, `last installment 841.21`, `total interest 433201.72` for 300k @ 0,8% × 360). Same pattern as US-003.
  - The `sum(SAC interest) < sum(PRICE interest)` invariant is the cleanest cross-system sanity check. It holds for any (P > 0, r > 0, n > 1) because SAC pays principal faster, shrinking the interest base. Useful as a regression guard whenever either schedule changes.
  - Reuse `ScheduleRow` / `roundMoney` / final-row-residual pattern verbatim — don't fork a SAC-specific row type. Downstream consumers (prepayment, charts, table, export) can treat PRICE and SAC schedules interchangeably.

## 2026-05-15 - US-005 — Prepayment engine (reduce-term + reduce-installment)
- Added `src/core/finance/prepayment.ts` exporting `applyPrepaymentReduceTerm(inputs, extra)` and `applyPrepaymentReduceInstallment(inputs, extra)`. Both accept `FinancingInputs` (PRICE | SAC via `system`) and a Decimal extra, return `{ schedule, summary }`.
- `PrepaymentScheduleRow` extends `ScheduleRow` with `baseInstallment` (what the row's installment would be without extra) and `extraPayment` (extra applied that month). `installment` is the total cash outflow; final partial rows recover `baseInstallment + extraPayment === installment` via a `splitFinalPayment` helper that caps recorded extra at the user's nominal extra.
- `PrepaymentSummary` carries totalPaid, totalInterest, interestSaved (vs base of the same system), originalTermMonths, newTermMonths, monthsReduced.
- Reduce-term: pay base + extra each month; PRICE base installment is constant, SAC base amortization is constant; loop ends when balance reaches 0 (term shortens) or `month === termMonths` (acts as a safety net for the extra=0 case where rounding residuals fall outside the `desiredTotal >= owed` window).
- Reduce-installment: each month recompute the base installment from (current balance, remaining-original-term). User pays recomputed-base + extra. With recurring extras the loan still finishes earlier than the original term (mathematically unavoidable — the PRD's "term fixed" reflects the recalculation rule, not the actual outcome). With extra=0 we short-circuit to the canonical base schedule to avoid cent-level rounding drift from the recursive PRICE/SAC recalculation.
- Tests cover the 4 (strategy × system) combinations with invariants (`balance` zero at end, `sum(amortization) === principal`, `interest + amortization === installment`, interestSaved > 0, installment-shape per strategy), plus zero-extra passthrough that matches `generatePriceSchedule` / `generateSacSchedule` row-for-row for both strategies, plus a cross-strategy invariant (`reduce-term ends earlier and saves more than reduce-installment for the same extra`), plus validation throws.
- Files changed: `src/core/finance/prepayment.ts`, `src/core/finance/prepayment.test.ts`, `scripts/ralph/prd.json`, `scripts/ralph/progress.txt`.
- Quality checks: `bun run typecheck` ✅, `bun run lint` ✅, `bun run test` ✅ (115 tests across 7 files, 32 new prepayment cases), `bun run build` ✅.
- **Learnings for future iterations:**

## 2026-05-15 - US-006 — Rent vs. buy comparison engine
- Added `src/core/finance/rent-vs-buy.ts` exporting `compareRentVsBuy(inputs): { buyTimeline, rentTimeline, summary }`, plus a reusable `annualToMonthlyRate(annual)` helper (`(1 + a)^(1/12) − 1` via Decimal.js `pow`).
- Inputs are flat (`propertyValue, downPayment, monthlyRate, termMonths, system?, monthlyRent, annualRentAdjustment, annualInvestmentReturn, annualAppreciation, monthlyOwnershipCosts, horizonMonths`). Schedule is built by reusing the PRICE/SAC engines (`generatePriceSchedule` / `generateSacSchedule`) — no duplicated finance logic.
- Buy timeline rows: `{ month, propertyValue, outstandingBalance, investedCapital, netWorth }`. Rent timeline rows: `{ month, rent, investedCapital, monthlyContribution, netWorth }`. Both timelines include month 0 (starting state) so length is `horizonMonths + 1`.
- Symmetric monthly model: the lower-spending side invests `|buyOutflow − rentOutflow|`; the higher spender contributes nothing (no borrowing). Buy outflow = installment + ownership costs; after `termMonths` the installment drops to zero. Both portfolios grow by the monthly investment rate first, then the contribution is added (so the new contribution doesn't earn interest in its own month).
- Property value compounds monthly via the same `annualToMonthlyRate` helper. Rent steps up at month 12, 24, 36, ... by `(1 + annualRentAdjustment)`.
- Summary: `bestScenario ('buy' | 'rent' | 'tie')`, `netWorthDifferenceFinal` (Decimal, `buy − rent`), `breakEvenMonth` (first m ≥ 1 where `buy.netWorth ≥ rent.netWorth`, else `null`). Tie tolerance is R$ 0.01.
- Tests cover all five PRD-required scenarios plus invariants and validation: equal-outcome (zero rates + free rent → tied at every month), buy-wins (high appreciation), rent-wins + no break-even (high return, no appreciation), break-even with crossover at m=44 (10% appreciation vs 6% return), timeline length, m=0 starting positions, monthly-contribution non-negativity, rent step-up at m=12/24, geometric appreciation, post-term horizon (loan paid off, only ownership costs continue), SAC system support, and 8 input-validation throw cases.
- Files changed: `src/core/finance/rent-vs-buy.ts`, `src/core/finance/rent-vs-buy.test.ts`, `scripts/ralph/prd.json`, `scripts/ralph/progress.txt`.
- Quality checks: `bun run typecheck` ✅, `bun run lint` ✅, `bun run test` ✅ (145 tests across 8 files, 30 new rent-vs-buy cases), `bun run build` ✅.
- **Learnings for future iterations:**
  - To reliably get a mid-horizon break-even crossover, the appreciation rate must exceed the investment return AND the buy-side outflow (installment + ownership) must initially exceed rent. With those parameters, the renter's portfolio grows faster early (renter is invested + receiving contributions) but the buyer's property growth eventually overtakes it. If `appreciation ≤ return`, buy will never catch up to a renter who started ahead. Useful for crafting deterministic test scenarios.
  - For the equal-outcome ("tie") test: zero rates everywhere + monthlyRent = 0 means each month the renter's contribution = the buyer's installment = that month's amortization (since rate = 0 → installment = principal/n). Both portfolios then grow by the same per-month amount and tie exactly at every m. This is the cleanest deterministic tie scenario; constructing one with non-zero rates is much harder due to compound-interest asymmetry.
  - `Decimal#pow(Decimal#div(...))` works for fractional exponents (verified `(1.12)^(1/12)` against expected ≈ 1.00949 within Decimal-precision tolerance). No need to fall back to `Math.pow` — keep everything in Decimal so precision stays controlled by the global `Decimal.set` from `financial-types.ts`.
  - The order "grow then contribute" (vs "contribute then grow") matters for one-month results: with "grow then contribute", a brand-new contribution doesn't earn interest in the same month. This matches typical end-of-month savings convention. Don't change without intent — it shifts every result.
  - PRD asymmetry: buy timeline doesn't include `monthlyContribution` while rent timeline does. Track the buyer's contribution internally (you need it for the buyer's invested capital) but don't expose it. Mirroring the AC field list exactly avoids unused-property noise downstream.
  - Validation-throw tests for finance engines: `expect(() => fn(badInputs)).toThrow(/fieldName/)` — the regex matches because the engine's error messages embed the field name (e.g. `"propertyValue must be greater than zero"`). Keeps tests resilient to small wording tweaks.

  - RHF + Zod with nullable defaults: `useForm<FormShape>({ resolver: zodResolver(schema), mode: "onChange", defaultValues })` works when `FormShape` has `number | null` fields. Do NOT pass the 3-generic form `useForm<TFieldValues, TContext, TTransformed>` — it conflicts with zodResolver's typing (zodResolver returns `ResolverResult<TFieldValues>`, not `ResolverResult<TFieldValues, TTransformed>`). If you need the strongly-typed parsed value inside `handleSubmit`, cast it (`values as unknown as FinancingFormValues`) — the resolver guarantees the schema ran successfully at runtime.
  - Zod `z.object().refine(...)` cross-field rules only fire when **every** individual field validation passes. For UI tests asserting the refine message, fill in ALL required fields with valid values before introducing the violation in the field of interest. If any sibling field is still invalid (e.g. `null` failing `.gt(0)`), the refine never executes and the message never appears. Same caveat applies to `superRefine` unless you flip it with `.superRefine` + early-return logic.
  - `react-hook-form` `Controller` is the right vehicle for the currency/percentage inputs (custom value type). Pass `value={field.value ?? null}` to handle the initial-null/default-null case. For the plain number input (prazo) and the native `<select>` (system), `register()` with `setValueAs` is simpler than `Controller`.
  - Derived read-only fields render best as `<output>` (not `readOnly <input>`): the label `htmlFor` still works with `getByLabelText`, `aria-live="polite"` announces updates to screen readers, and the element doesn't get caught by form-level focus traversal or `register`-style scans. Style with the same input box classes for visual consistency, plus the `.font-tabular` utility for monetary cells.
  - The cleanest way to publish RHF form state to a page-level context without re-rendering everything is to call `setFinancing(values)` from inside `handleSubmit`. Watching `useWatch` and pushing to context on every keystroke is tempting but causes cascading re-renders of every downstream card and is hard to invalidate when fields go invalid mid-typing. Use submit as the explicit publish point; use `useWatch` only for *intra-form* derived fields (the financed-amount / annual-rate outputs).
  - When a hand-rolled shadcn primitive is exported alongside a helper function from the same file (e.g. `parseBRL` + `CurrencyInput`), `react-refresh/only-export-components` warns. Move the helper to its semantic home — `parseBRL` belongs next to `formatBRL` in `lib/formatters/currency.ts`. Tests should import the helper from the formatter module, not from the component.
  - Native `<select>` styled with shadcn classes is enough for the PRICE/SAC binary choice (and any future enum selector). Don't add `@radix-ui/react-select` for a 2-option dropdown — the CLAUDE.md "no new deps without clear justification" rule applies. The styled native select supports keyboard navigation out of the box and integrates with RHF `register("system")` without any wrapping.
  - When changing `src/app/App.tsx` to consume a new provider, remember to update `src/app/App.test.tsx`'s render helper too (it doesn't inherit the main.tsx provider chain). Wrap with the new provider next to `ThemeProvider`. If you forget, every App-level test fails with "must be used within a *Provider".
